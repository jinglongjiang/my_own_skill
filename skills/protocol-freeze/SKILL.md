# protocol-freeze：冻结协议

## 为什么要冻结
看到结果以后再定成功标准，任何结果都能被解释成成功。冻结的作用是让"通过"这两个字有分量：判据、划分、对照臂都在数字出现之前写死，之后的结论别人没法说是挑出来的。

先读 `references/shared/evidence-rules.md`。输入：候选卡、先例对照、前筛结论。输出目录 `research/protocols/<候选编号>/`。
命令里的 `$SKILL_DIR` 指本文件所在目录，运行时换成它的绝对路径；`research/` 指用户项目里的研究工作区，不在技能目录下（见 `references/shared/workspace.md`）。

## 写协议
按 `assets/protocol-template.md` 的章节写 `PROTOCOL.md`。每节的要点和理由如下，细则与常见漏洞见 `references/design-rules.md`。

**0 主张与不可声称。** 主张写成可被否定的句子，不预设成因。不可声称清单从 `prior-art-duel` 抄过来，再加上方法本身的理论边界（例如标签是事后量时，不能引用要求期望值的定理）。

**1 母体与输入。** 权重、数据、代码各自的路径与哈希。

**2 数据划分。** 训练 / 开发 / 最终测试三块，按完整 episode（或 case）划分，不按状态随机划分——同一 episode 的状态共享同一个世界的未来，随机划分等于泄漏。最终测试块只读一次，写明在什么文件出现之后才允许读。列出每一块此前被哪些实验用过。

**3 抽样规则。** 写成可以复算的确定规则（哪些 case、每个取几个状态、随机种子怎么来）。不按结局或模型表现挑样本。写明规模不够时怎么缩减（缩什么、不缩什么）。

**4 评分与标签口径。** 训练时用的评分函数必须和部署时实际执行的是同一个公式，包括过滤、惩罚、平滑、常数项。实现后要有一步"用训练侧代码重建部署分数"的校验。标签和评分在边界情况（终止、截断）上不一致的地方，预先写明处理规则。

**5 对照臂。** 最少四臂的思路：
| 臂 | 回答的问题 |
|---|---|
| 原样不动 | 基线 |
| 同数据同预算，原目标继续训练 | 提升是不是只来自多训练 |
| 同数据同预算，用新信息但不用新机制 | 提升是不是只来自新信息 |
| 提出的方法 | —— |
相邻两臂之间只差一个因素。各臂共用的损失项必须是同一段代码、同一权重。各臂的超参搜索规模相当，选择准则相同。

**6 裁决条件。** 全部写成**相对同期对照臂的配对差**，这样不需要先知道基线的绝对值就能预注册。至少包含：
- 整体收益：方法 vs 原样
- 独立贡献：方法 vs "同信息不用机制"那一臂（这是方法贡献的全部证据）
- 安全/代价的非劣效界：写明界值，并说明它是人为设定的容忍上限还是由噪声推导
- 保持性：原本表现好的条件不能明显变差，用置信界而不是点估计
写明检验方法、校正方式、主家族包含哪些比较。写明每种结果组合对应的结论（全过、只过一半、离线指标升而闭环不升）。任何对照臂"意外有效"都不自动判死，除非它直接否定了独立贡献。

**7 阶段与停止。** 正确性校验 → 吞吐实测 → smoke → 数据 → 训练 → 开发集选择并冻结 → 最终测试。写明哪些情况自动停止并保存证据。预算上限和样本下限都写数字；超预算时的缩减规则预先定好。

**8 披露。** 已知但无法消除的限制（例如数据来源不可追溯），固定记为"未验证"，写明它影响哪条结论。不把缺失的证据标成通过。

## 冻结
```
python3 "$SKILL_DIR/scripts/freeze.py" lint   research/protocols/C01     # 查缺章节
python3 "$SKILL_DIR/scripts/freeze.py" freeze research/protocols/C01     # 取哈希，写 FREEZE.json
```
把哈希告诉用户，并写进交给执行方的指令里。
`freeze.py` 只锁定协议文本和修订文件的哈希。它不判断模板是否真的填完（`lint` 只查章节和"待定"字样），也不校验协议里列的权重和数据——这些资产的哈希要在执行的第一阶段核对。冻结前自己通读一遍协议，确认没有空着的格子。

## 冻结之后要改
不改 `PROTOCOL.md` 本体。写一份 `AMENDMENT-n.md`：改哪条、为什么、**修订时已经看到了哪些数据**、其余条款不变。然后：
```
python3 "$SKILL_DIR/scripts/freeze.py" amend research/protocols/C01 AMENDMENT-1.md --seen "……" --reason "……"
python3 "$SKILL_DIR/scripts/freeze.py" verify research/protocols/C01
```
判断一项修订是否正当，看它动的是什么：
- 预算、排程、并发、工程实现 → 正当，随时可改。
- 无法满足的前置门槛（证据不存在）→ 可以降为已声明的限制，但不能标成通过。
- 判据、划分、对照臂、抽样 → 只有在没看到任何相关结果时才可改；看到了再改，结论要带上这个限制。
- 为了让结果过线而放宽 → 不改。

## 回应对设计的质疑
第三方指出问题时逐条判断：成立就写修订并说明落实方式；不成立就给出证据。常见的成立质疑：评测口径被采样改变了、训练和测试共用了 case、对照臂差了不止一个因素、引用了不适用的理论保证、把工程上限说成统计推导。

## 汇报
给出：协议路径与哈希；由你做的参数选择各一行理由（这些需要用户认可）；尚未验证、放进第一阶段去核实的前提；估算成本并标明是推算还是实测。
