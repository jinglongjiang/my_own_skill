# method-build：实现与运行

## 为什么需要这个环节
筛查、协议、交接都不产生结果。一个课题如果连续几轮都停在"前提未核实""证据不存在""门槛未通过"，问题往往不是不够严谨，而是没有人动手。很多前提只有在写代码、跑一个小例子时才会暴露，而且暴露得比审计快。这个技能的任务是用最小的代码拿到第一个真实数字。

先读 `references/shared/evidence-rules.md` 和 `references/shared/profile.md`。
命令里的 `$SKILL_DIR` 指本文件所在目录，运行时换成它的绝对路径；`research/` 指用户项目里的研究工作区，不在技能目录下（见 `references/shared/workspace.md`）。

## 什么时候自己做，什么时候交给执行代理
| 情况 | 谁做 |
|---|---|
| 原型在本地几小时内能出数字（冻结权重上的评测、小规模微调、离线查表） | 自己做 |
| 需要先弄清代码里某个行为才能写协议 | 自己做，这本身就是调查 |
| 流程已经连续两次停在核查或交接 | 自己做下一步，不再转一手 |
| 多臂、多 seed、要占满远程 GPU 一个夜班以上，且协议已冻结 | `exec-handoff` 交给执行代理 |
自己做的原型同样受协议约束：不读保留测试块，判据不因为是原型而放宽。原型得到的数字标为开发集证据，不当作最终裁决。

## 步骤

### 1. 调查（改代码之前）
确认：实际操作的是哪个项目目录和分支；工作区有没有别人未提交的改动；要改的函数从哪里被调用、输入从哪来、输出被谁消费；相关开关在训练期和部署期是否都生效；现有的测试和运行方式。
沿"定义 → 调用点 → 输入来源 → 分支条件 → 状态变化 → 输出消费者"走一遍再下判断。只看了局部就只能说"怀疑"，不能说"根因"。
移植或对齐参考实现时，把所有分支（else、提前返回、回退路径、异常路径）列出来逐个对，不只复现主分支；没有证据不改阈值、不做"看起来等价"的化简。

### 2. 最小原型
- 新代码放在独立目录，原工程只读；通过导入或挂接复用原函数，不复制粘贴原逻辑（复制的那份会和原版悄悄分叉）。
- 只实现验证关键假设所必需的部分。配置项、日志美化、通用化都留到确认有效之后。
- 不顺手重构，不清理无关代码，不动别人的改动。

### 3. 三个必须先过的检查
这三项加起来通常不到半小时，能挡掉大多数"跑了一夜才发现白跑"：
1. **退化一致**：把新机制的强度设为零（或等价的关闭方式），输出必须与原系统逐例一致。不一致说明挂接方式本身改变了行为，后面的任何差异都无法归因。
2. **重建一致**：训练侧自己算的分数，和部署代码在同一批状态上算的分数对比，偏差超过阈值就停。
3. **损失与梯度的单元测试**：用手算得出答案的小例子验证损失值；确认梯度只流向打算更新的参数；确认边界情况（并列、空集合、终止候选）不产生 NaN。
细则见 `references/build-checks.md`。

### 4. Smoke
在**与正式运行相同的代码路径**上跑最小规模：几个 case、几步更新、保存、重新加载、评测。确认：能启动；关键分支确实被执行（打日志或计数）；输入输出形状和取值范围合理；输出文件生成且能被下游读取；指标没有 NaN，出现 0% 或 100% 这类端点值时查明原因（小样本下可能是正常的）；运行用的确实是改过的代码。
同时记下每个 episode 或每步的实际耗时，用它估算正式运行的时间，替换掉之前的推算。
smoke 不过就不启动正式任务。

### 5. 启动长任务
按瓶颈选机器（GPU 训练去远程 GPU；CPU 密集的仿真看核数和负载）。启动用：
```
python3 "$SKILL_DIR/scripts/jobwatch.py" start --dir runs/<名称> -- <命令>
```
它记录 PID 和进程启动时刻、把输出写进日志、结束时写退出码。启动后立刻确认：进程在、日志有有效输出、用的是预期的代码和配置、初始指标在合理范围。

### 6. 盯任务
```
python3 "$SKILL_DIR/scripts/jobwatch.py" status --dir runs/<名称> --stall <该任务正常的最长静默秒数>
python3 "$SKILL_DIR/scripts/jobwatch.py" wait   --dir runs/<名称> --timeout <秒>
```
`status` 用 PID 文件和 /proc 判断存活，不用 `pgrep -f` 或 `ps | grep`——那类写法会把查询命令自己算进去，导致永远显示"还在跑"。它区分五种状态：运行中、正常结束、失败结束、疑似卡住、进程消失但没有退出码。最后一种不能当作完成。
`--stall` 的取值来自这个任务正常的输出间隔，不随手定一个数。判断不了是否还在推进时，直说"无法确认"。

### 7. 出问题时
非零退出、异常、输出与预期不符、长时间无进展：停下，保存证据，定位，做最小修复，重新验证当前这一步，然后才继续。同一个问题修了两三次还不过，就回头检查最初的判断——是不是只看了局部、改的代码有没有真的被调用、跑的是不是旧代码或旧进程。

### 8. 交回
得到第一批数字后：
- 用 `result-verdict` 的工具复算并做稳健性检查，再对外说结论。
- 原型有利 → 写成或更新候选卡，进 `protocol-freeze` 做正式验证。
- 原型不利 → 确认是方法的必要条件不成立，还是原型本身的问题（三个检查都过了吗），然后在 `research-ledger` 落账。
汇报写：做了什么、验证了什么、证据在哪、当前状态、还有什么没验证。
