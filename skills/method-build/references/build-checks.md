# 实现阶段的三项检查

## 1. 退化一致
目的：证明"挂接新机制"这件事本身不改变系统行为。
- 给新机制一个强度参数（阈值、权重、步数），取零值时应该数学上等于原系统。
- 在一批固定 case 上逐例比较：结局、时长、每步选中的动作。完全一致才算过；少量不一致要解释到具体原因（例如浮点并列）。
- 例：并列仲裁规则把并列阈值设为 0，在约 1.9 万步里只有 2 步与原始决策不同，且都是分数完全相等的并列。这样后续任何差异才能归因到规则本身。
- 不过时常见原因：挂接改变了内部状态更新的顺序；重新实现时漏了一次取整或类型转换；原函数有只在某个阶段生效的分支。

## 2. 重建一致
目的：证明训练侧和部署侧算的是同一个量。
- 在同一批记录的状态上，用训练侧代码算出每个候选的分数，与部署代码当时记录的分数逐项相减。
- 阈值预先定（例如 1e-5），超过就停。
- 部署多出来的每一项都要进公式：过滤掩码、风险惩罚、平滑后的候选命令、常数偏置。
- 边界情况单独核：终止候选是否仍加自举项、全部候选都被过滤时掩码是否失效。

## 3. 损失与梯度
- **数值**：构造 2–3 个候选的小例子，手算损失，与代码输出比。
- **方向**：对一个应该被纠正的错误次序，走一步梯度后分数差应该朝正确方向移动。
- **范围**：冻结的参数梯度为空或为零；要更新的参数梯度非零。
- **边界**：标签并列的对子被排除；集合只剩一个候选时不报错、不产生 NaN；掩码候选不进损失。
- **尺度**：记录损失各项的量级。一项比另一项大几个数量级时，小的那项实际上不起作用。

## Smoke 清单
- [ ] 与正式运行同一入口、同一配置加载方式
- [ ] 关键分支被执行的证据（日志或计数）
- [ ] 一步更新 → 保存 → 重新加载 → 评测 全链路
- [ ] 输出文件能被下游脚本读取
- [ ] 指标不是 NaN；出现 0% 或 100% 时逐例看一眼原因（几个 case 的小样本本来就可能全成功或全失败，这不自动算失败，但要确认不是评测没生效）
- [ ] 确认运行的是改过的代码（打印版本标记或文件哈希）
- [ ] 实测耗时已记录，正式运行时间按它重估
- [ ] 磁盘余量够放全部产物

## 启动后清单
- [ ] `jobwatch.py status` 显示进程存活
- [ ] 日志里已有属于这次运行的有效输出
- [ ] 使用的 GPU、配置、输出目录与预期一致
- [ ] 第一个指标读数在合理范围
- [ ] 定好下一次检查的时间点（按该任务正常的输出频率）
