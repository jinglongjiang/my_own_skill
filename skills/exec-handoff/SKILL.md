# exec-handoff：执行交接与回执评估

先读 `references/shared/evidence-rules.md` 和 `references/shared/profile.md`。

## 一、写指令

### 原则
执行方没有你这边的上下文，只会照字面做。所以指令里只放它需要的东西，判断留在协议里：
- **协议是唯一权威。** 指令只引用协议路径和哈希，不复述协议内容。两处都写就会出现两处不一致。
- **短。** 用户要把它粘贴过去，长了就没人核对。正文放文件里，粘贴的部分十行以内。
- **写清楚不许做什么。** 执行方遇到障碍时的本能是绕过去。把最不能绕的几条写成禁止项。
- **停止比完成重要。** 告诉它什么情况必须停、停的时候留什么证据。一次干净的停止只花几分钟，一次带错跑完要花一个夜班再加一轮返工。

### 结构
把完整指令写到 `research/handoffs/<编号>.md`（模板 `assets/handoff-template.md`），包含：目标（一两句）、只读输入及哈希、可复用代码、分阶段步骤、禁止项、自动停止条件、交付物与报告格式。
然后给用户一段可直接粘贴的短文本：读哪个文件、协议哈希、是否连续执行、最关键的一两条禁止项、何时停止。

### 报告格式要求（写进指令）
要求执行方的报告：每个结论标"已验证通过 / 未验证 / 已确认失败"并给出原始文件；区分"任务未完成"和"科学结论为负"；停止时写明唯一的解阻条件和估计成本；不把缺失的证据标成通过；不自行放宽门槛或修改协议。

### 发出前自查
- 协议已冻结，`freeze.py verify` 通过。
- 指令里的每个路径都存在（实际列一下目录）。
- 每条禁止项都有对应的协议条款。
- 有没有哪个门槛要求的证据可能根本不存在？有的话先自己查一下，或者在指令里写明"无法获得时记为未验证并停止报告"。

## 二、评估回执

执行方交回报告时，先读报告正文和它指向的原始证据文件，再下判断。不只看摘要。

### 第一问：执行合规吗
| 检查 | 怎么查 |
|---|---|
| 协议哈希、输入哈希 | 报告里的值与冻结记录一致 |
| 有没有碰禁止项 | 尤其是保留测试块的读取计数 |
| 停在门槛上时是否保存了证据 | 证据文件存在且能复算 |
| 有没有自行放宽门槛或改协议 | 对比冻结哈希 |
| 报告的结论是否超出证据 | 逐条对原始文件 |
合规地停下来是正确执行，要明确告诉用户"它停得对"。

### 第二问：停下的原因属于哪一类
| 类别 | 特征 | 处理 |
|---|---|---|
| 前提不成立 | 协议假设的事实是错的 | 修正前提，必要时回到前筛 |
| 证据不存在 | 门槛要求的材料拿不到 | 给用户列方案：找替代证据 / 降为披露 / 重做上游；用户选定后写修订 |
| 预算或工程 | 吞吐、磁盘、排程 | 自己重算一遍。执行方的估算常常过于保守（用最慢的条件外推全部），看能否只改排程 |
| 实现缺陷 | 校验没过 | 让它修实现，协议不动 |
| 科学结果为负 | 裁决条件没满足 | 交给 `result-verdict`，不在这里改判据 |
"预算或工程"类不需要修订协议里的科学条款；"证据不存在"类需要修订但不能把缺失标成通过。

### 第三问：我自己之前说错了什么
报告经常顺带暴露协议作者的错误：估算偏了、前提没核实、某个字段记错了。直接说明哪条不对、正确的是什么、影响哪个决定。同时防止过度修正：复核后原结论成立的，就说成立。

### 汇报
按"现象 → 问题 → 证据 → 方案 → 推荐"写。开头一句话回答用户最关心的：执行方做得对不对，卡在哪。需要继续时附上给执行方的下一段短指令。
